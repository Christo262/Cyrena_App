What Are API References?

API References are structured technical documents that capture the deep knowledge of a codebase — service contracts, method signatures, integration patterns, architecture rules, and usage examples. They are the authoritative source of truth for how a library or extension works.

Unlike Sticky Notes (quick reminders and conventions), API References are comprehensive, grounded in actual source code, and designed for intense coding sessions. They describe real method signatures, real contracts, and real behavior — not generic or hypothetical descriptions.

The key difference: API References are importable and exportable. This means a library can ship its own documentation, and any developer using that library can import it into their Cyréna chat. The AI immediately understands the library's surface — no context building, no repeated explanations.

The API References UI

In every Cyréna Coding Assistant chat, the API References button appears in the toolbar. Clicking it opens a dedicated page where you can view, create, edit, import, and export API Reference documents.

The API References page lists all documents for the current chat. Each entry shows the title, summary, keywords, and provides actions to edit, export, or delete. The toolbar at the top supports importing .aiapi files and manually creating new API Reference documents.

The .aiapi File Format

API References are exported as .aiapi files — JSON-formatted documents with a distinctive extension that makes them easy to identify, share, and import. The .aiapi extension is purely for differentiation; the content is standard JSON and can be inspected or edited with any text editor.

For Library Authors

If you are building a shared library with Cyréna, you should create API References for every public surface intended for consumers:

  • Models exposed across feature boundaries
  • Global services and their public methods
  • Guards, interceptors, and resolvers with non-trivial behavior
  • Shared components with documented inputs and outputs
  • Route structure and lazy-loaded feature entry points
  • Extension entry points and builder methods

Once documented, export the API References as a .aiapi file and include it in your package. Consumers import it and the AI immediately knows how to use your library correctly — following the patterns, respecting the contracts, and avoiding common mistakes.

For Library Consumers

When you install a library that includes a .aiapi file, import it into your Cyréna chat before you start coding. The AI will:

  • Know the correct method signatures and parameter types
  • Follow established architecture rules and patterns
  • Use the library's extension points correctly
  • Avoid anti-patterns documented in the reference
  • Generate code that aligns with the library's design philosophy

This eliminates the "learning curve" phase where the AI guesses at APIs and produces incorrect or outdated code. The documentation is authoritative because it was written by the library author, grounded in the actual source.

Best Practices

Tips for Writing API References

  • Ground every document in real source code — include actual method signatures, not generic descriptions
  • Document the "why" alongside the "what" — architecture rules, design decisions, and constraints
  • Use keywords that developers would search for when trying to solve a problem with your library
  • Keep references focused — one document per major service, contract, or feature area
  • Update references when the public API changes — version them alongside your code
  • Export and ship .aiapi files with every release of your library
  • Import references before starting work on a new codebase — the AI reads them automatically
  • Treat public interfaces as stable contracts — breaking changes require updated documentation

API References vs. Sticky Notes

Aspect API References Sticky Notes
Purpose Deep technical documentation for services, contracts, and APIs Quick reminders, rules, and architectural decisions
Scope Public surfaces intended for consumers Internal conventions and project-specific notes
Format Structured documents with title, summary, keywords, content Free-form text notes
Exportable Yes — as .aiapi files for shipping with libraries No — tied to the specific project chat
Grounded in Code Yes — real signatures, real contracts, real behavior No — can be abstract or conceptual
When to Use When building or consuming shared libraries and extensions When establishing project conventions and rules

Both systems work together. Sticky Notes capture the project's personality and conventions. API References capture the library's technical surface. Together, they give the AI complete context — both the "how we do things here" and the "how this library works."
