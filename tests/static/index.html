Offline Models

Models running locally via Ollama. Great for privacy, no API costs, but require decent hardware.

Ollama – qwen3:30B

Offline
  • Good all-rounder for local use — handles chat and general development tasks competently.
  • Runs entirely on your own hardware; no data leaves the machine.
  • Medium-sized model strikes a balance between capability and resource usage.

Ollama – qwen3:32B

Offline
  • Slightly larger variant of the 30B model with similar overall behaviour.
  • Marginally better at nuanced reasoning due to the extra parameters.
  • Expect similar resource requirements and response quality.

Ollama – qwen3-coder:32B

Offline
  • Specialised for coding tasks — fine-tuned to produce cleaner, more idiomatic code.
  • Good for boilerplate generation, refactoring, and explaining complex logic.
  • Not as strong on open-ended chat or non-code creative tasks.

Ollama – qwen3-coder:480B

Offline
  • Very large model — extremely thorough but noticeably slower on consumer hardware.
  • Best reserved for tasks where quality trumps speed (e.g., architecture reviews).
  • Requires significant RAM and GPU resources to run comfortably.

Ollama – minimax-m2.7

Offline
  • Reliable everyday workhorse — good for chat, brainstorming, and general dev assistance.
  • Consistent output quality without surprising failures.
  • A safe default when you just need something that works.

Ollama – gemma4:31B

Offline Default
  • Bloody brilliant for its size — punches well above its 31B weight class on chat, general development, and function calling.
  • Function calling is remarkably reliable — handles tool use better than some significantly larger models.
  • My default for general assistance when I want local, private inference without sacrificing capability.

Ollama – gpt-oss:120B

Offline
  • Produces code quickly — great for rapid prototyping and iterative development.
  • Occasionally omits parts for brevity; a gentle reminder ("please include the full function") fixes this.
  • Good balance of speed and capability for a 120B parameter model.

Cloud Models

Models accessed via cloud APIs or Ollama Cloud. No local hardware constraints, but require internet and may incur costs.

Ollama – gpt-oss:120B-cloud

Cloud
  • Same model as the offline 120B, but running on Ollama Cloud.
  • Frees up local resources; useful if your machine cannot comfortably host 120B parameters.
  • Same brevity quirk applies — remind it when you need complete implementations.

Ollama – mistral-large-3

Cloud
  • Extremely picky about how it wants to be interacted with and how tool calls are supposed to happen.
  • Throws errors frequently — the model seems very sensitive to prompt formatting and function-calling conventions.
  • Cloud reliability issues — because it is such a large model running on Ollama Cloud, the cloud interaction sometimes fails outright.
  • Overall, a frustrating experience. I would not recommend it for development-agent work.

OpenAI – gpt-5

Cloud Outstanding
  • Outstanding across all use-cases (chat, Arduino, ESP-IDF, .NET, etc.).
  • Occasionally needs a prompt to perform a web search, especially for brand-new releases (e.g., .NET 10.0).
  • Rarely refuses to answer; when it does, a short "look it up online" cue resolves the issue.

Ollama – qwen3-coder:480B-cloud

Cloud
  • Very poor experience (only tried with .NET).
  • The model becomes defensive, starts cutting code, and fabricates details.
  • Function calling is unreliable — it may describe an intention without actually invoking it.

Ollama – deepseek-v3.1:671B-cloud

Cloud
  • Lazy — responds to the prompt but then does nothing until you explicitly say "do the research".
  • Even after a web query it replies with a vague "I did the search" and provides no concrete results.

kimi-k2.6

Cloud Favourite
  • My current favourite across dev tasks.
  • Stands out for taking time to understand the project and its structure before making any changes — it never just dives in blind.
  • This careful, context-first approach means fewer mistakes and less back-and-forth correcting misunderstood scope.

Ollama – minimax-m2.7:cloud

Cloud
  • Works well for single-project .NET development.
  • Success hinges on very explicit, structured prompts:
    • Use sticky notes to capture hard rules.
    • Keep an "Overview" of the application in an "API References" sticky note.
  • With these constraints the model can build entire applications that are easy to test, maintain, and debug — and continuously update the API References & sticky notes as it learns, making it ideal for function calling.

General Tips for Getting the Most Out of These Models

1

Set the thinking level

Low for speed, medium for more thoroughness, high only when you truly need deep reasoning (and are okay with longer latency).

2

Force web searches

Most models will not search unless you ask. Example: "Please look up the latest ESP-IDF API changes and summarize them."

3

Structure your prompts

For the larger cloud models (especially minimax-m2.7): begin with a brief overview, list hard rules as bullet points, provide any relevant API reference, and end with a clear action request.

4

Remind about full code

When a model omits code, gently remind it: "Please include the full implementation of the function; do not skip any lines."
